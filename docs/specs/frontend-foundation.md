# Spec: Frontend Foundation — shadcn Base Components & Feature-Based Structure

- **Status:** Ready for review (all open questions resolved)
- **Date:** 2026-09-29
- **Stack:** React 19, TanStack Router + Query + Form, oRPC, Tailwind v4, shadcn (`base-lyra` style, Base UI primitives), `packages/ui` workspace package

## 1. Objective

Give the web app a predictable, easy-to-extend frontend foundation:

1. A complete set of **base UI primitives** generated from shadcn and owned in `packages/ui`.
2. A small set of **composed shared components** (layout, data display, feedback, forms) built only from those primitives, so pages stop re-implementing the same markup.
3. A **feature-based folder structure** (screaming architecture) in `apps/web/src`, where each business domain owns its components, hooks, and logic, and routes stay thin.
4. **Import rules** that keep the structure from eroding, enforced by lint.

## 2. Scope

### In scope

- Add missing shadcn primitives to `packages/ui` and remove the unused AI chat items (§4.2).
- Composed shared components in `apps/web/src/shared` (§4.3).
- Move existing web code (`components/`, `hooks/`, `lib/`, fat route files) into `features/*` and `shared/*` with **no behavior change**.
- Application shell (sidebar navigation + header) replacing the duplicated tab-nav layouts.
- Lint-enforced import boundaries.
- README section: "Adding a feature" and "Adding a UI primitive".

### Out of scope (v1)

- Visual redesign / new brand theme (tokens stay as generated by `base-lyra` + `neutral`).
- Storybook or a component documentation site.
- i18n.
- New product features — this is a structural refactor plus foundation.
- Server (`apps/server`) and `packages/api` structure.

## 3. Glossary

| Term                 | Meaning                                                                                                               |
| -------------------- | --------------------------------------------------------------------------------------------------------------------- |
| **Primitive**        | A shadcn-generated component in `packages/ui` (button, dialog, table…). Domain-agnostic, no data fetching.            |
| **Shared component** | An app-level component in `apps/web/src/shared` composed from primitives (e.g. `DataTable`, `PageHeader`). No domain. |
| **Feature**          | A business domain folder in `apps/web/src/features/<name>` (auth, organizations, admin, audit-log).                   |
| **Public API**       | A feature's `index.ts`: the only module other code may import from that feature.                                      |
| **Route file**       | A TanStack Router file under `src/routes`. Declares guards/loaders and composes feature components.                   |

## 4. Architecture

### 4.1 Layers and dependency direction

```
routes/  ──►  features/*  ──►  shared/  ──►  @base-template/ui
   │              │               │
   └──────────────┴───────────────┴──►  app/ (providers, clients) — only via explicit exports
```

- Dependencies point **one way**: `routes → features → shared → ui`. Never the reverse.
- A feature **must not** import another feature's internals; it may import another feature's public API (`@/features/<name>`) only when the dependency is explicit and acyclic.
- `shared/` and `packages/ui` never import from `features/` or `routes/`.
- `packages/ui` never imports from `apps/web` (it is app-agnostic and reusable).

### 4.2 Primitives (`packages/ui/src/components`)

Generated with the shadcn CLI from `packages/ui` (`components.json` already configured, style `base-lyra`). Every base component is a shadcn registry item; no hand-rolled primitives. Files are owned code: edits are allowed but must stay domain-agnostic.

**Removed from the base:** the AI chat items currently in `packages/ui` (`attachment`, `bubble`, `marker`, `message`, `message-scroller`) are deleted; they are unused by the web app and not part of a generic template. A project that needs them re-adds them with `shadcn add`.

| Group        | Already present                               | To add                                                                 |
| ------------ | --------------------------------------------- | ---------------------------------------------------------------------- |
| Actions      | button                                        | button-group, toggle, toggle-group                                     |
| Forms        | input, input-group, label, textarea, checkbox | field, select, native-select, combobox, radio-group, switch, input-otp |
| Overlays     | dropdown-menu, tooltip                        | dialog, alert-dialog, sheet, popover, command                          |
| Navigation   | —                                             | sidebar, breadcrumb, tabs, pagination                                  |
| Data display | card, empty, skeleton                         | table, badge, avatar, separator, scroll-area, item, kbd                |
| Feedback     | sonner                                        | alert, spinner, progress                                               |

**Forms:** the shadcn `form` item is built on react-hook-form. This app uses **TanStack Form**, so `form` is **not** added; `field` (layout-only: `Field`, `FieldLabel`, `FieldDescription`, `FieldError`) is used instead, bound to TanStack Form in `shared/components/form` (§4.3).

### 4.3 Shared components (`apps/web/src/shared`)

```
shared/
  components/
    layout/     app-shell.tsx, app-sidebar.tsx, app-header.tsx, page-header.tsx, section-nav.tsx
    feedback/   loader.tsx, load-error.tsx, no-permission.tsx, empty-state.tsx
    data-table/ the table system (see data-table.md; replaced the original data/ DataTable)
    form/       form-field.tsx (TanStack Form ↔ Field bindings), submit-button.tsx
    overlays/   confirm-dialog.tsx
  hooks/        (cross-feature hooks only, e.g. use-debounced-value.ts)
  lib/          (cross-feature pure helpers, e.g. date-range.ts)
```

| Component                                           | Purpose                                                                                                                             |
| --------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| `AppShell`                                          | `SidebarProvider` + `AppSidebar` + `AppHeader` + content `Outlet`. Hosts the impersonation banner slot.                             |
| `AppSidebar`                                        | Navigation groups from a typed config (not hard-coded JSX); items can declare a visibility predicate (e.g. superadmin, permission). |
| `PageHeader`                                        | Title, optional description, optional actions slot, optional breadcrumb.                                                            |
| `SectionNav`                                        | Typed tab navigation over TanStack `Link` (replaces the duplicated tab markup in settings and admin layouts).                       |
| `DataTable`                                         | Server-driven table (see data-table.md): sort, filters, pagination, loading skeleton, empty state, error state with retry.          |
| `FormField` / `SubmitButton`                        | Renders a TanStack Form field through `Field*` primitives with label, description, and first error; submit shows pending state.     |
| `ConfirmDialog`                                     | `alert-dialog` wrapper for destructive actions: title, description, confirm label, pending state, async `onConfirm`.                |
| `Loader`, `LoadError`, `NoPermission`, `EmptyState` | Existing feedback components moved here, rebuilt on `spinner` / `empty` / `alert`.                                                  |

Shared components are **presentational**: they receive data and callbacks via props, and never call oRPC or better-auth directly.

### 4.4 Feature structure (`apps/web/src/features/<name>`)

```
features/<name>/
  components/   presentational + container components for this domain
  hooks/        data hooks (TanStack Query / oRPC / better-auth client)
  lib/          pure logic, co-located *.test.ts
  index.ts      public API — the only import surface for other modules
```

- Folders are created only when needed (no empty `hooks/` for a feature without hooks).
- **Container / presentational split:** hooks fetch and mutate; components under `components/` that call hooks are containers; pure-render components take props. Pure logic lives in `lib/` and is unit-tested.

Initial features, mapped from current code:

| Feature          | Receives (current location → new)                                                                                                                                                                            |
| ---------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `auth`           | `sign-in-form`, `sign-up-form`, `check-inbox-screen`, `user-menu`; `lib/auth-errors`, `lib/verify-email-status`                                                                                              |
| `invitations`    | `accept-invitation-sign-up`, `accept-invitation-signed-in`; `lib/accept-invitation-errors`; invitations settings page content                                                                                |
| `organizations`  | `org-switcher`; `lib/org-layout-guard`; general + members settings page content; `hooks/use-org-member-directory`, `lib/member-directory`                                                                    |
| `access-control` | `can-gate`; `hooks/use-can`, `use-active-member-role`, `use-org-roles`, `use-platform-can`; `lib/can-state`, `lib/permission-load-error`, `lib/role-catalog`, `lib/platform-role`; roles editor page content |
| `audit-log`      | `lib/audit-log-display`; org + platform activity page content                                                                                                                                                |
| `admin`          | `impersonation-banner` (+ `lib/impersonation-banner`), `lib/ban-expiry`, `lib/org-limit-input`; users, user detail, organizations page content                                                               |

`app/` holds wiring that is neither a feature nor a shared component: providers (`theme-provider`, query client), `auth-client`, `orpc` client, and the sidebar navigation config.

Final placement of individual files may deviate from this table when an import-boundary violation reveals a better owner; deviations are recorded in the task document.

### 4.5 Route files

A route file may only:

1. Declare the route (`createFileRoute`), `beforeLoad` guards, loaders, search-param validation.
2. Compose feature components (and shared layout components) into the page.

A route file must not contain domain logic, query/mutation definitions, or components longer than composition glue. Target: **≤ ~60 lines** per route file (guideline, not a hard gate).

### 4.6 Import rules & aliases

| Alias                            | Resolves to                             |
| -------------------------------- | --------------------------------------- |
| `@base-template/ui/components/*` | primitives (unchanged)                  |
| `@/shared/*`                     | `apps/web/src/shared/*`                 |
| `@/features/<name>`              | `apps/web/src/features/<name>/index.ts` |
| `@/app/*`                        | `apps/web/src/app/*`                    |

Enforced with oxlint `no-restricted-imports` via `overrides` in `.oxlintrc.json` (verified against the installed oxlint `1.85.0`; patterns use gitignore globs — `@/features/*/**` matches deep imports, `@/features/*/*` does **not**):

| Files                    | Forbidden import patterns                    | Why                                       |
| ------------------------ | -------------------------------------------- | ----------------------------------------- |
| `apps/web/src/**`        | `@/features/*/**`                            | only a feature's public API is importable |
| `apps/web/src/shared/**` | `@/features`, `@/features/**`, `@/routes/**` | shared never depends on features/routes   |
| `packages/ui/**`         | `@/*`, `web`, `web/**`                       | primitives stay app-agnostic              |

Convention that makes the first rule work: **inside a feature, imports are relative** (`./components/foo`, `../lib/bar`); the `@/features/<name>` alias is used only across features and from routes. A deep alias import is therefore always a boundary violation, with no per-feature configuration.

`apps/web/components.json` aliases are updated so `shadcn add` run from the app targets the correct places (`components` → `@/shared/components`).

## 5. Requirements

### F0 — Folder structure

**F0.1 Structure exists**

- GIVEN the migration is complete
- THEN `apps/web/src` contains only `app/`, `features/`, `shared/`, `routes/`, plus entry files (`main.tsx`, `index.css`, `env*.ts`, generated `routeTree.gen.ts`)
- AND the old top-level `components/`, `hooks/`, `lib/`, `utils/` folders no longer exist.

**F0.2 Public API only**

- WHEN code outside `features/x` imports `@/features/x/components/foo`
- THEN `pnpm lint` fails with a boundary error.

**F0.3 Direction**

- WHEN a file in `shared/` imports from `@/features/*` or `@/routes/*`
- THEN `pnpm lint` fails.

### F1 — Primitives

**F1.1 Available**

- GIVEN §4.2 "To add" list
- THEN each primitive exists in `packages/ui/src/components`, generated via the shadcn CLI with the project style, and `pnpm check-types` passes.

**F1.2 Chat items removed**

- GIVEN the migration is complete
- THEN `attachment`, `bubble`, `marker`, `message`, `message-scroller` no longer exist in `packages/ui`, and nothing in the repo imports them.

**F1.3 Theming**

- GIVEN light and dark mode
- THEN every primitive renders using the `globals.css` tokens only (no hard-coded colors added by hand).

### F2 — Shared components

**F2.1 AppShell**

- GIVEN an authenticated user inside an active organization
- THEN pages render inside `AppShell` with a sidebar (dashboard, organization settings, and — only for superadmins — platform admin) and a header (org switcher, theme toggle, user menu).
- AND on narrow viewports the sidebar collapses into a sheet.

**F2.2 SectionNav**

- GIVEN the organization settings and platform admin layouts
- THEN both use `SectionNav` with a typed item list, and the active item is visually marked and exposes `aria-current="page"`.

**F2.3 DataTable states**

- GIVEN a `DataTable` bound to a query
- THEN it shows skeleton rows while pending, `EmptyState` when there are no rows, `LoadError` with retry on error, and page controls when the query is paginated.

**F2.4 FormField**

- GIVEN a TanStack Form field with a validation error
- THEN `FormField` renders the label, the first error message, and sets `aria-invalid` on the control and `aria-describedby` to the error.

**F2.5 ConfirmDialog**

- GIVEN a destructive action (remove member, cancel invitation, delete role, ban user)
- THEN it is confirmed through `ConfirmDialog`, the confirm button shows a pending state during `onConfirm`, and the dialog closes only on success.

### F3 — Migration without behavior change

**F3.1 Parity**

- GIVEN the migration is complete
- THEN every route from `auth-multitenant-rbac.md` §7 behaves as before (same guards, same permission gating, same error handling).

**F3.2 Tests move with code**

- GIVEN a moved `lib/*.ts` module
- THEN its `*.test.ts` moves next to it and `bun test` reports the same number of passing tests or more, 0 failing.

**F3.3 Thin routes**

- GIVEN any route file after migration
- THEN it contains no query/mutation definitions or domain logic (§4.5).

### F4 — Developer experience

**F4.1 Adding a feature**

- GIVEN the README "Adding a feature" section
- THEN a developer can create `features/<name>` with its `index.ts`, add a route that composes it, and add a sidebar entry by editing only: the new feature folder, one route file, and the navigation config.

**F4.2 Adding a primitive**

- GIVEN the README "Adding a UI primitive" section
- THEN it documents the exact `shadcn add` command to run and from which directory.

## 6. Proposed delivery slices

1. **Primitives** — add §4.2 components to `packages/ui` (generated code, low risk).
2. **Structure + boundaries** — create `app/`, `shared/`, `features/`, aliases, lint rules; move feedback components and `app/` wiring.
3. **Shared components** — `AppShell`, `SectionNav`, `PageHeader`, `DataTable`, `FormField`, `ConfirmDialog` (+ unit tests for pure logic).
4. **Feature migration** — one slice per feature group (`auth` + `invitations`, `organizations` + `access-control`, `audit-log` + `admin`), thinning routes as each moves.
5. **Docs** — README sections (F4).

## 7. Non-functional requirements

- **No behavior change** in §F3; this is a refactor + additions.
- **Accessibility:** keyboard navigation and focus management come from Base UI primitives; shared components must not break them (labels, `aria-*` from F2.4, focus return after dialogs).
- **Testing:** pure logic stays unit-tested with `bun test`; shared components' non-trivial logic (pagination math, nav-visibility predicate, error selection in `FormField`) is extracted to pure functions and unit-tested. UI tasks otherwise use ordinary checks (`pnpm check-types`, `pnpm lint`, manual smoke of §7 routes).
- **Bundle:** routes stay code-split by TanStack Router; primitives are imported per file (`@base-template/ui/components/<name>`), never through a barrel.
