## 1. Objective and scope

The academic offering and its logistics: which subject is taught in which course by which teacher (`offering`, "Materias por Grado"), the teacher assignment lifecycle, student enrollment in the offerings of a course, classrooms, time blocks and the weekly timetable (generated by a deterministic solver, viewed per course, teacher or student).

## 3. API

Routers in `routers/sige/scheduling.ts`: `offeringRouter`, `assignmentRouter`, `enrollmentRouter`, `classroomRouter`, `timeBlockRouter`, `scheduleRouter`. All are `sigeProcedure.use(requirePermission(...))`; no input contains `organizationId` (R3.2); `NOT_FOUND` for other tenants and out-of-scope rows (R1.15). Lists that can exceed ~50 rows use the shared list input with a `*-list-config.ts` (R3.8): offerings, assignments, enrollments, classrooms. Time blocks are a bounded list (R3.9). Errors per R3.5; deletes with dependents return `HAS_DEPENDENTS` with the §4.2 message.

| Procedure             | Permission                        | Input                                                  | Output                                                                                                  | Scope                                                                                                                                                                                  |
| --------------------- | --------------------------------- | ------------------------------------------------------ | ------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `schedule.get`        | `schedule:read` or `student:read` | `{ view: "course", courseId? } \| { view: "teacher" }` | `WeeklySchedule`                                                                                        | managers: any course; teacher: `view: "teacher"` (own offerings) or a course inside their scope (STU-02 tab); student: own course only (`courseId` omitted = own); parent: not allowed |
| `schedule.generate`   | `schedule:generate`               | `{ campusId?: string, courseId?: string }`             | `{ assigned: number, conflicts: number, courses: number, skipped: { courseId, courseName, reason }[] }` | targets the current academic year; `courseId` wins over `campusId`                                                                                                                     |
| `schedule.deleteSlot` | `schedule:update`                 | `{ slotId }`                                           | `{ deleted: true }`                                                                                     |                                                                                                                                                                                        |

```ts
type WeeklySchedule = {
  title: string; // "Horario del grado 6-01", "Horario de {profesor}"
  rows: {
    time: string; // "07:00 - 08:00"
    isBreak: boolean; // a row is a break only when every block sharing it is a break
    cells: (SlotCell | null)[]; // Monday..Friday (index 0..4)
  }[];
};
type SlotCell = {
  slotId: string;
  offeringId: string;
  subjectName: string;
  teacherName: string | null;
  classroomName: string;
  courseName: string;
};
```

Rows are the distinct `(start, end)` pairs of the relevant blocks sorted by start time (`buildScheduleRows`): for a course, the blocks of its campus, shift and year; for a teacher, the union over the campuses and shifts of the courses they teach. A cell shows the slot whose `start_time` equals the row start.

### 4.3 Behavioural rules

- SCH-R1 **Permissions.** SCH-01…10 and 12: owner, admin, coordinator (`enrollment`, `offering`, `classroom`, `time_block`, `schedule` grants of foundation §4.2). SCH-11: managers all; teacher `schedule:read` own (via `view: "teacher"` or a course in scope); student own course; parent and viewer none.
- SCH-R2 **Offering = central join.** Grades, attendance, enrollments, schedule slots and report-card comments hang off `offering`. `offering.options` is the only selector other modules use; it never returns an offering outside the caller's scope.
- SCH-R3 **Teacher assignment sync.** `assignment.assign` and `offering.createBulk` (with a teacher) set `offering.teacher_person_id` and upsert one `teacher_assignment` row (`activo`, `assignment_date` = today in `America/Bogota`, `academic_year` of the course). `assignment.update` changes only status and notes. `inactivo` keeps the teacher on the offering but removes the teacher's row scope (§4.3 of the foundation); `temporal` keeps it. `assignment.delete` clears the teacher and the row. Reassigning an offering that already has slots is refused if the new teacher is busy at any slot time: `CONFLICT` "El profesor ya tiene clases en el mismo horario ({curso}, {día} {hora})."
- SCH-R4 **One teacher per offering** (OD-23): "Una materia de un grado tiene un único profesor."
- SCH-R5 **Bulk enrollment** (R2.9). In one transaction: for each selected student, set `student.course_id = course` **and `student.campus_id = course.campus_id`** (prototype behaviour, G-SCH-1); insert one `activa` enrollment per offering of the course (year = `course.academic_year`) skipping existing `(student, offering, year)`; ignore non-active students with `BAD_REQUEST` on the whole call. Capacity: when `current + selected > maxStudents` and `allowOverCapacity` is not set the call fails with the capacity message; the web offers "Matricular de todos modos" (resends with `allowOverCapacity: true`) so over-capacity stays a confirmable warning as in R2.9. A course without offerings fails with "El grado no tiene materias asignadas."
- SCH-R6 **Offering delete** removes the assignment row and is refused per §4.2.
- SCH-R7 **Course change vs enrollments.** Changing a student's course in STU-03 does not alter existing enrollments (prototype). Enrollment rows whose course differs from the student's current course are flagged `isStale` and shown with a muted badge "Grado anterior"; coordinators resolve them by editing the status (`retirada`) and enrolling the student in the new course. Grade sheets and attendance sheets list students by current course membership (R2.10), not by enrollment.
- SCH-R8 **Enrollment `final_score`** is an administrative field edited by hand (prototype); it is not derived from grades and never recomputed.
- SCH-R9 **Double-booking.** Per R2.14 and its extension (G-SCH-2): within one academic year, no two slots may overlap in time on the same day for the same classroom, the same teacher or the same course. The unique key catches identical start times; the service checks overlapping intervals (`a.start < b.end and b.start < a.end`) inside the generation transaction.
- SCH-R10 **Generation** (`schedule.generate`, solver in `sige-core`, R3.18/R3.20):
  1. Take an institution-wide advisory lock; a second concurrent call waits.
  2. Targets: courses of the current academic year filtered by campus or course. Delete every slot of the target courses (regeneration replaces them; v1 has no manual placement).
  3. Busy sets are seeded from the slots of non-target courses (teachers and classrooms).
  4. Per course, take its offerings sorted by `hours_per_week` desc then id; use the non-break blocks of the course's campus, shift and year ordered by `order_num`; round-robin hour by hour: for each offering and weekly hour pick a weekday (rotation `(offeringIndex + hour × 2) mod 5`, preferring days where the offering is not yet placed), then the first block such that the course has no class in that cell, the teacher (if any) is free and a room is free; room candidates = rooms of the subject's preferred type, then the course's home classroom, then any `aula`.
  5. Unplaced hours count as conflicts. Courses whose campus and shift have no blocks are listed in `skipped` with reason "Sin bloques de tiempo para {sede} · {jornada}." and their hours count as conflicts (`Sabatina` courses always fall here, G-SCH-5).
  6. Persist slots, write `schedule.generated`. The solver is a pure deterministic function (same input, same output); the result is stable across runs.
     The room type heuristic (name contains "fisica" → `cancha`; "natural" or "tecnolog" → `laboratorio`; otherwise `aula`) is the prototype's; OQ-SCH-2.
- SCH-R11 **Time blocks.** `academic_year` is the institution's current year at creation. Editing times, campus or shift of a block that is in use is rejected: "No se pueden cambiar los horarios de un bloque con clases programadas."
- SCH-R12 **Inactive campuses** (module 02) are excluded from the campus selects of SCH-08/10 and from generation.

## 7. Testing and acceptance

### 7.1 Tests

- **Unit** (`sige-core`): the solver with fixtures (a tiny institution, then a seed-sized one): never overlaps a room, a teacher or a course; places exactly `hours_per_week` slots when capacity allows; counts conflicts when blocks are scarce; honours preferred room types; skips courses without blocks with the reason; deterministic output for identical input; non-target busy sets respected. `timesOverlap` (adjacent, nested, equal, one-minute overlap); `buildScheduleRows` (break merging, sorting, teacher union); bulk-enrollment planner (skip existing, capacity arithmetic); preferred-room-type heuristic.
- **API integration** (Postgres): each uniqueness and delete rule with its exact message; `createBulk` offering idempotent and transactional; `enrollment.createBulk` atomic (inject a failure on the 3rd student: nothing persists), idempotent re-run (`created = 0`), sets course and campus, capacity error and override path; stale flag after a course change; `assignment.assign` creates or reuses the offering, reassign conflicts with a busy teacher, `inactivo` removes teacher scope in `offering.options` and grade-sheet access; `schedule.generate` on the seed yields 0 conflicts (P3 exit criterion), is serialized by the advisory lock under two concurrent calls, and never touches non-target courses; DB unique prevents identical classroom/day/start; service rejects overlapping intervals for classroom, teacher and course; `schedule.get` scoping (teacher sees only own, a student sees only own course, a parent is `FORBIDDEN`, another tenant's course is `NOT_FOUND`); `offering.options` filtered by teacher scope; permission matrix per role for every procedure (teacher: `schedule.get` only; student: `schedule.get` own; parent/viewer: none) and the generated tenant-isolation suite.
- **Web**: lists render empty/loading/error and respect permissions; SCH-02 candidate list resets on course change and shows the capacity confirm flow; SCH-06 skipped/created toasts; SCH-08 JSON validation; SCH-10 overlap and in-use messages; SCH-11 renders break rows, slot deletion for managers only, role-specific titles and empty states; SCH-12 progress → result states including `assigned = 0` and `skipped`; stories for `WeeklySchedule`, `CheckList` variants and new presentational components.

### 7.2 Acceptance

- SCH-01/02: bulk enrollment creates students × offerings once, moves the student into the course and campus, reports created/skipped, never duplicates; edits limited to status, score and note; stale enrollments are visible.
- SCH-03/04/05/06: assigning a teacher updates both the offering and the assignment; one teacher per offering; deleting an offering with dependents is refused with the §4.2 message; `inactivo` stops the teacher from grading it.
- SCH-07/08/09/10: every rule of §4.1; blocks in use cannot be deleted or re-timed.
- SCH-11: each role sees exactly its schedule; slot deletion is manager-only and audited.
- SCH-12: on the demo seed (≈ 58 offerings) generation reports 0 conflicts; running it twice yields the same slots; classroom, teacher and course double-booking is impossible at both DB and service level.
