## Objective

Adopt the reference `template-dashboard` design (full look: rounded, `text-sm`, Geist) for the authenticated shell (icon-collapsible sidebar with org switcher, collapsible nav, footer user menu, breadcrumb header) and the auth pages (split `AuthCard` on `/sign-in`, `/sign-up`, check-inbox, verify-email, accept-invitation), plus Google-only social sign-in, while preserving existing better-auth, invitation, onboarding and RBAC behaviour.

## Constraints

- Base UI stays (no Radix). Import boundaries from `frontend-foundation.md` apply; `shared/**` never imports `@/features/**`.
- Do not touch the user's uncommitted `packages/infra/.env.schema` edit or `Makefile` except where T6 must add the Google variables (then keep the user's existing hunk intact and do not commit their unrelated change without asking).
- OAuth secrets are never committed; tests mock Google.
- Conventional commits, no AI attribution. Formatters run before commit so lefthook hooks are no-ops.
- Deterministic stories (no `Math.random`, no unfixed dates, no network).

## T6 decision record

Verified against the installed better-auth 1.7.5 source (`node_modules/better-auth/dist`, `@better-auth/core`) and `@better-fetch/fetch` 1.3.2:

- **Client error shape (T5 follow-up a):** failed client calls resolve to `{ data: null, error }` and `fetchOptions.onError` gets `{ error, ... }`; `error` is FLAT: parsed API body (`{ code, message }`) spread with `{ status, statusText }`. There is no nested `error.error`; the old reader always fell back to generic messages. `betterAuthErrorMessage` now reads flat (message, then statusText, then fallback); `authFormErrorMessage` was removed (consolidated). `runAuthAction` wraps a client call for the forms: HTTP error and rejected promise both become an inline message.
- **`socialProviders.google`:** `{ clientId, clientSecret }`; per-provider `requireEmailVerification` is opt-in (default false, independent of `emailAndPassword.requireEmailVerification`), so it is set to `true`: an unverified Google email on a NEW account fails with `email_not_verified` and gets no session. Startup validation: `resolveGoogleCredentials` (pure) throws naming the missing variable.
- **Account linking (`oauth2/link-account.mjs`):** an existing user with no linked Google account is linked only if `(provider trusted || userInfo.emailVerified)` AND (`requireLocalEmailVerified` default true => local `emailVerified`) AND `accountLinking.enabled !== false`; otherwise the callback returns `account_not_linked`. A provider in `trustedProviders` would link even an unverified provider email, so `trustedProviders: []` is set explicitly (with `enabled: true`, `requireLocalEmailVerified: true`).
- **Carrying the invitation id:** `POST /sign-in/social` accepts `additionalData` (object); `generateState` spreads it into the signed OAuth state; `getOAuthState()` (exported from `better-auth/api`) reads it in the callback request. It is client-supplied (docs: "must not be trusted"), which is fine here: it can only make sign-up stricter. `getOAuthState` throws outside a request (scripts/tests), so the hook catches and treats that as "not OAuth".
- **Hook:** `databaseHooks.user.create.before(user, ctx)` runs before the user row exists; a thrown `APIError` with a `code` inside the callback becomes a redirect to `errorCallbackURL` with `?error=<code>&error_description=<message>` (`redirectOnError`). Code `INVITATION_EMAIL_MISMATCH`. Only a pending, unexpired invitation is enforced; requires `emailVerified` and case-insensitive equality. An EXISTING user signing in with Google is linked, not created, so the hook does not run for them; they still accept on `/accept-invitation/$id` (recipient check unchanged, tested).
- **Client `signIn.social`:** body accepts `provider`, `callbackURL`, `errorCallbackURL`, `newUserCallbackURL`, `additionalData`; the redirect plugin navigates to the returned `url`. Errors return via `?error=` on `errorCallbackURL`; `error_description` is never rendered (URL-controlled), known codes map to fixed text (`oauth-error.ts`).
- **Endpoint:** `GET /api/public/auth-providers` (Hono, `apps/server/src/public-routes.ts`) returns `{ providers: ["google"] }` from the same env as `createAuth`; web query `useEnabledProviders` returns `[]` while loading and on any failure. Server env vars are declared in `apps/server/.env.schema`; `packages/infra/.env.schema` does not declare server vars (it only imports `NODE_ENV` from the server), so it was not touched and the user's uncommitted hunk there stays unstaged and uncommitted.
- Web wiring: forms own `useSocialSignIn` (so the submit button is disabled while a redirect is pending) and render `SocialSignInButtons` directly; the `socialSlot` props were removed. Sign-in now returns to `/accept-invitation/$id` when `invitationId` is threaded (spec §4.2), otherwise `/dashboard`. Google sign-in on invitation sign-up uses the invitation page as `callbackURL` and `errorCallbackURL` (with the token) so the password sign-up stays usable.
- T5 follow-ups: (a) done (flat shapes, tests with the real shape), (b) sign-in/up network reject shows the inline alert (`runAuthAction` test), (c) mismatch sign-out navigates to `/sign-in` with `invitationId`.
- Test approach: Google's token endpoint is stubbed via `fetch`; the ID token is an unsigned JWT (the provider only decodes it in `getUserInfo`). No real OAuth app.
- Pending: manual Google round trip with real dev credentials; manual smoke of the button states.

## T7 decision record

- **T6 follow-ups:** (a) `useSocialSignIn` resets pending on `pageshow` with `persisted` (pure `isBfcacheRestore`); (b) `fetchEnabledProviders` now rejects on non-2xx, network error, bad JSON and malformed body; the query retries 3 times with capped exponential backoff (1s, 2s, 4s, max 10s), only a successful answer stays fresh 5 min, and the button is hidden while unresolved or failed; (c) all three forms pass `disabled={isSubmitting}` to `SocialSignInButtons` (inside `form.Subscribe`); (d) `socialSignInTargets` gained `callbackPath` and `errorParams`, used by invitation sign-up; (e) `betterAuthErrorBody` reads only better-fetch error objects (plain object with numeric `status`); thrown `Error`s (including `ORPCError`, which has `status`) are never read, so every caller keeps its own fallback.
- **Error-message rule (checked against every caller of `betterAuthErrorMessage`/`betterAuthErrorCode`, 40+ call sites):** callers either pass a better-auth client error (flat shape, server message shown) or a TanStack Query / oRPC error (thrown `Error`, always the caller's fallback, as before T6). - **Dark/light audit:** hard-coded colours in files touched by the feature: `verify-email-page` `text-red-500` replaced by `text-destructive` (and the field now uses `FormField` for `aria-invalid`/`aria-describedby`).
